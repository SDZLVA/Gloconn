# Glooconn v0.19.0 — Release Notes

**Release date:** August 2026  
**Codename focus:** Travel Packages (Milestone 13)  
**Preceded by:** [v0.18.0](./v0.18.0.md) (Live Hotels)

---

## Release overview

v0.19.0 ships **Recommended Travel Packages**: intelligent flight + hotel combinations composed from existing live (or mock) domain results. Packages are a **product-layer** feature — not a new provider, not a parallel search pipeline, and not a redesign of the stable search architecture.

Users who search with both flights and hotels see a **Recommended Packages** hero section on the results page when composition succeeds. Individual flights and hotels remain available in the existing results list below.

## Highlights

- **Travel Packages** — recommended flight + hotel combinations with combined price and match score
- **Shared `TravelPackage` model** — vendor-agnostic product construct
- **`PackageComposer`** — pure, deterministic composition (no HTTP, no AI, no provider knowledge)
- **`SearchResponse.packages`** — always present; empty array when composition is not possible

## Architecture

```
Search UI
  → POST /api/search
  → SearchService
  → SearchOrchestrator
      → FlightsProvider / HotelsProvider / TransportProvider (parallel, ADR-037)
      → PackageComposer(flights, hotels, request)   ← product layer
  → SearchResponse { hotels, flights, …, packages }
  → UI (Recommended Packages + existing results list)
```

| Layer | Role |
|-------|------|
| Providers | Unchanged — still return `Flight[]` / `Hotel[]` only |
| `PackageComposer` | Pure composition + scoring in `lib/packages/` |
| Orchestrator | Composes packages only when both arrays are non-empty |
| UI | Displays packages; does not re-call providers |

**No `PackagesProvider`.** Packages never trigger vendor HTTP.

## Travel Packages

### Shared model

`TravelPackage` includes: `id`, embedded `flight` / `hotel`, `flightId`, `hotelId`, `totalPrice`, `currency`, `nights`, `score`.

`Flight` and `Hotel` models were **not** modified.

### Composition rules

- Matching currencies only (mismatches skipped; no FX)
- Candidate caps (8 flights × 8 hotels) + max 20 packages
- Stable ids: `pkg-{flightId}-{hotelId}`
- Deterministic score ordering (budget fit, flight/hotel quality, price, convenience)

### Partial failure (ADR-037)

| Case | `packages` |
|------|------------|
| Flights fail, hotels OK | `[]` |
| Hotels fail, flights OK | `[]` |
| Either side empty | `[]` |
| Both succeed with results | Composed |

`totalCount` still counts domain results only (packages are derived, not double-counted).

## Known limitations

1. **SerpAPI round-trip** — `departure_token` return enrichment may HTTP 400 → outbound-only flight fallback (carry-forward from v0.17.0).
2. **Candidate bias** — pre-selection favors cheaper options; “Recommended” lodging can skew budget.
3. **UI volume** — composer may return up to 20 packages; no separate UI top-N cap yet.
4. **No package booking** — cards are informational only.
5. **No hotel images on model** — package cards use the same placeholder pattern as hotel cards.
6. **Rooms / child ages** — inherited hotel provider limitations unchanged.
7. **Mock transport** — buses and trains remain mock.
8. **Ops** — restart `npm run dev` after `.env.local` changes.

## Configuration (operators)

Packages require **both** flights and hotels to return results. Live example:

```env
USE_MOCK_PROVIDERS=false
FLIGHTS_PROVIDER=serpapi
HOTELS_PROVIDER=serpapi
SERPAPI_API_KEY=<secret — never commit>
SERPAPI_DEEP_SEARCH=false
```

Default remains **mock** for all domains. `.env.local` is gitignored.

No new environment variables for packages.
